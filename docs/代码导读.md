# 代码导读

> 读之前先记住一句话：**这个项目就是把一张 RAG 流程图变成了代码。**
> 流程图有两段：**离线阶段（建库）** 和 **在线阶段（问答）**。
> 你只要能在代码里找到图上的每一个方块，这个项目就懂了 80%。
>
> **本文所有路径都从项目根目录 `E:\RAGproject` 开始写**，例如 `app/api/v1/documents.py`。

## 一、先看这张图（和你视频里那张一一对应）

```
┌───────────────────────── 离线阶段：构建知识库（上传时跑一次） ─────────────────────────┐
│                                                                                      │
│   保险条款.pdf ──→ 解析 ──→ 切分 ──→ 一堆「知识片段」 ──→ 向量化 ──→ 向量数据库        │
│   (第 1 页…)      去乱码    900字/块    每块带页码偏移      变 1024 个数     Milvus     │
│                                                                                      │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                    ↑
                          两段用的是同一个「向量模型」
                                    ↓
┌───────────────────────── 在线阶段：检索增强（每次提问跑一次） ─────────────────────────┐
│                                                                                      │
│   用户问「尊享e生2026版免赔额是多少？」                                                 │
│        │                                                                             │
│        ├─→ 问题向量化 ──→ 向量检索（+关键词检索）──→ 召回 5 段知识片段                  │
│        │                                                                             │
│        └──────────────────────────────────────────→ 拼 prompt：                       │
│                                                       【知识片段 1】…免赔额 1 万元…    │
│                                                       【知识片段 2】…                 │
│                                                       用户问：免赔额是多少？           │
│                                                             │                        │
│                                                             ↓                        │
│                                                        大模型生成                     │
│                                                             ↓                        │
│                                        「免赔额是 1 万元 [1]」──→ 点 [1] 跳回原文第 7 页 │
│                                                                                      │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

**关键点只有三个**，其余都是细节：

1. **先建库、再问答**。上传文档时把文本切成块、算好向量存起来；提问时才有东西可查。
2. **提问时也是"先查资料、再让模型说"**。模型不是凭记忆回答，是拿着你给的五段话在复述。
3. **两段必须用同一个向量模型**。文档用 A 模型、问题用 B 模型，两边算出来的数字不在一个世界里，检索会"看起来正常但全错"。

## 二、图上的每个方块，对应哪段代码

### 离线阶段（上传文档时）

| 图上的方块 | 代码位置 | 这一步在干什么 |
|---|---|---|
| 保险条款.pdf | `app/api/v1/documents.py` → `upload_document()` | 收文件、存盘、建任务、丢后台 |
| 解析 | `app/ingestion/pipeline.py` → `loader.load()`（解析器在 `app/ingestion/loader.py`） | 按后缀选解析器；PDF / DOCX 配了 token 就优先 MinerU（失败直接报错），否则用 pypdf / python-docx |
| （去乱码） | `app/ingestion/cleaner.py` → `clean_text()` | 去零宽字符、压空行 |
| **切分** | `app/ingestion/splitter.py` → `split_text()` | 900 字一块，**并记下每块在原文的起止位置** |
| 知识片段 | `app/models/orm.py` → `Chunk` 表 + Milvus | 一块存两处：关系库（主数据）+ 向量库（索引） |
| **向量化** | `app/indexing/embedding.py` → `embed_documents()` | 一段文字 → 1024 个浮点数 |
| 向量数据库 | `app/indexing/milvus_store.py` → `upsert()` | 存进 Milvus，同时挂上 BM25 支持关键词检索 |

### 在线阶段（每次提问时）

| 图上的方块 | 代码位置 | 这一步在干什么 |
|---|---|---|
| 用户提问 | `app/api/v1/chat.py` → `chat()` | 收问题，返回一条 SSE 流 |
| （管会话） | `app/services/chat_service.py` → `ask_stream()` | 找会话、读历史、存消息 |
| **总调度** | `app/pipeline/rag.py` → `RAGWorkflow.run_stream()` | ★ 下面几步都从这里发起 |
| （改写问题） | `app/retrieval/rewrite.py` → `condense_question()` | 把「它」换成具体名词；没有历史就跳过 |
| **问题向量化** | `app/indexing/embedding.py` → `embed_query()` | 和离线用的是同一个模型 |
| **向量检索** | `app/indexing/milvus_store.py` → `hybrid_search()` | 向量 + 关键词两路各捞 10 条，合并 |
| （挑重点） | `app/retrieval/rerank.py` → `rerank()` | 逐条判断"能不能回答这个问题"，留 5 条 |
| **拼 prompt** | `app/generation/prompt.py` → `build_messages()` | 把 5 段资料 + 规矩 + 问题拼成一段话 |
| **大模型** | `app/generation/llm.py` → `stream_text()` | 流式生成，一个字一个字往外吐 |
| （标出处） | `app/generation/citation.py` | 把 `[1]` 翻译成"哪份文件第几页第几个字" |

## 三、为什么代码比图多出几步？

你的图是**原理版**，代码是**工程版**。多出来的四步，每一步都对应图解决不了的一个真实问题：

| 图上没有的 | 代码里有 | 不这么做会怎样 |
|---|---|---|
| 只有向量检索 | 加了 BM25 关键词检索 | 问「QKV」「2026版」这种精确词，向量检索会漏；反过来问「大模型胡说」，关键词检索漏 |
| 检索完直接用 | 加了精排 | 向量检索只管"意思像"，排序经常不准，前 5 条里混进无关段落 |
| 问题原样去查 | 加了改写 | 第二句问「它呢？」，这句话没有语义，检索必然失败 |
| 直接拼给模型 | 加了"资料不足就说不知道"的规矩 | 模型会用自身知识编一个看起来很真的答案 |
| 答案就是一段话 | 加了引用解析和偏移定位 | 用户没法验证答案真假，也没法跳回原文 |

**所以读代码时的心态应该是**：图告诉你"整体在干什么"，代码里的每一步都是在补图的漏洞。看到不认识的步骤，先问"它在防哪种失败"，比死记函数名有用得多。

## 四、用保险那个例子走一遍代码

用户问：**「尊享e生2026版免赔额是多少？」**

```
1. app/api/v1/chat.py::chat()
   收到 JSON → 交给 service
   ↓
2. app/services/chat_service.py::ask_stream()
   新建会话 #7 → 读历史（空）→ 存下用户这句话
   ↓
3. app/pipeline/rag.py::RAGWorkflow.run_stream(
       question="尊享e生2026版免赔额是多少？", kb_ids=[1], history=[])
   ↓
4. 改写：history 为空 → 直接返回原问题（省一次模型调用）
   ↓
5. 检索：app/indexing/embedding.py::embed_query(...) → [0.02, -0.11, ...] 1024 个数
   app/indexing/milvus_store.py::hybrid_search 拿这 1024 个数 + 原始文字，去 Milvus 里捞
       ├─ 向量路：捞到"免赔额 1 万元，年度累计"那一段
       └─ 关键词路：捞到写着"尊享e生2026版"的条款封面
   ↓
6. 精排：app/retrieval/rerank.py 两路合并 8 条 → 逐条打分 → 留 5 条，免赔额那段 0.87 排第一
   ↓
7. 拼 prompt（app/generation/prompt.py::build_messages）：
       [1] 来源：保险条款.pdf 第 7 页（第三章 免赔额）
           本产品年度免赔额为 1 万元……
       [2] 来源：保险条款.pdf 第 1 页
           尊享e生2026版……
       问题：尊享e生2026版免赔额是多少？
   ↓
8. 大模型流式输出（app/generation/llm.py::stream_text）：
       「尊享e生2026版的年度免赔额是 1 万元 [1]……」
   ↓
9. 解析出 [1]（app/generation/citation.py）→ 映射到 chunk_id="3_00012" → 第 7 页、字符 435~601
   ↓
10. 前端渲染（web/app.js）：答案里的 [1] 变成蓝色角标，下面一张引用卡片
    用户点 [1] → GET /api/v1/chunks/3_00012 → 弹出原文那一段
```

第 5 步的"两路"、第 6 步的精排、第 9 步的偏移，就是上面那张"多出来的四步"表里的东西。

## 六、术语对照（别人说的时候你能对上）

| 别人说的 | 图上对应 | 大白话 |
|---|---|---|
| 知识库 / KB | 离线阶段那个框 | 一堆你上传的文档 |
| chunk / 知识片段 | 切分后面那排小文档图标 | 文档被切成的小段 |

| 精排（rerank） | （图上没有） | 再一条条细看，挑出真能用的 |
| prompt 拼接 | 拼接那个框 | 把资料和问题拼成一句话交给模型 |
| grounded | （图上没有） | 这次回答有没有出处 |
| 幻觉 | （图上没有） | 模型编造了资料里没有的内容 |

## 八、目录结构：每个包在干什么

这一节当字典用，写代码前扫一眼就知道该往哪放。

### 后端 `app/`

| 目录 / 文件 | 职责 | 里面有什么 | 不该放什么 |
|---|---|---|---|
| `app/main.py` | 应用装配 | 挂路由、挂静态文件、启动检查、缓存头 | 业务逻辑 |
| `app/api/v1/` | **HTTP 层** | 路由、参数校验、异常→状态码 | 数据库查询、检索、拼 prompt |
| `app/services/` | **业务编排** | 跨模块的顺序问题（删库先删向量）、会话与消息落库、摘要 | 检索算法、prompt 文本 |
| `app/pipeline/` | **流程编排** | `rag.py`：改写→检索→评估→生成→引用→校验 | 具体怎么召回、怎么调模型 |
| `app/retrieval/` | **检索** | `hybrid.py`（双路召回+RRF）、`rerank.py`、`rewrite.py` | 写库、拼 prompt |
| `app/generation/` | **生成** | `prompt.py`（唯一 prompt 来源）、`llm.py`、`citation.py` | 检索、数据库 |
| `app/indexing/` | **向量层** | `milvus_store.py`（schema/读写）、`embedding.py`、`expression.py`（过滤表达式） | 文档解析、业务流程 |
| `app/ingestion/` | **离线链路** | `loader.py`、`parsers/`、`cleaner.py`、`splitter.py`、`pipeline.py` | 检索、生成 |
| `app/models/` | **数据定义** | `orm.py`（表）、`schemas.py`（接口出入参） | 业务逻辑 |
| `app/core/` | **基础设施** | `config.py`、`db.py`、`milvus.py`、`logging.py` | 业务判断 |

### 其他目录

| 目录 | 作用 |
|---|---|
| `scripts/` | 一次性工具：`init_milvus.py` 建表、`dev_check.py` 全链路自检、`smoke_test.py` 只测向量层、`calibrate.py` 量阈值 |
| `tests/` | 单元测试（切分偏移、过滤表达式），不依赖数据库 |
| `web/` | 单页前端，无构建：`index.html` + `app.js` + `style.css` |
| `docs/` | 本文档 |
| `deploy/` | Milvus standalone 的 docker-compose（换机器时用） |
| `data/` | 运行时生成：`rag.db`（SQLite）、`files/`（上传的原始文件）、`samples/`（示例文档）。**不进 git** |

### 分层依赖方向（只能单向）

```
api  →  services  →  pipeline  →  retrieval / generation
                                        ↓
                              indexing / ingestion
                                        ↓
                                   models / core
```

**下面不能反过来 import 上面。** 判断标准：

- `core` 不认识任何业务概念（只知道“数据库”和“配置”）
- `models` 不 import services
- `retrieval` 不知道 HTTP 和数据库会话
- `api` 里出现 `pymilvus`、`MilvusClient` 就说明分层被穿透了

### 为什么这么分

1. **换实现只动一层**：换向量库改 `indexing/milvus_store.py`；换模型改 `.env`；换前端只动 `web/`
2. **能绕过上层测试**：`splitter.py` 只依赖标准库，所以 `tests/` 不需要数据库就能跑
3. **出问题知道去哪找**：检索不准看 `retrieval/`，回答乱看 `generation/prompt.py`，进度不动看 `ingestion/pipeline.py`
